一、怎么用这份清单
======================================================================

【1. 适用范围与文件位置】

这份清单测的是 dsh-ui-block 这个包，不是某个实例。三个代码位置：

  归档仓库    D:\cursor编程文件\工作区1相关\工作区1\DSH自研插件\dsh-ui-block（本目录，只读参考）
  3080 插件体 D:\DSH Pack Launcher\dsh-packs\dsh-origin-3080\profiles\web\.dsh-launcher-plugin-bodies\dsh-ui-block
             另有一份实体副本：...\profiles\web\node_modules\dsh-ui-block（不是 junction，见已知问题 3）
  4000 插件体 D:\DSH Pack Launcher\dsh-packs\dsh-fallback-4000\profiles\web\.dsh-launcher-plugin-bodies\dsh-ui-block

被测数据都落在 DSH_HOME 下（3080 的 DSH_HOME 是 D:\DSH Pack Launcher\dsh-packs\dsh-origin-3080）：

  块文件      <DSH_HOME>\ui-blocks\<name>.uiblock（HTML 片段，无元信息行、无 <html> 包装）
  历史        <DSH_HOME>\ui-blocks\.history\<name>\base.uiblock 与 log.json（一行一条 {at, patch}）
  钉子        <DSH_HOME>\ui-blocks\.pins.json（键 "<name>|<nodeKey>|<index>"，值是 epoch 毫秒）
  浏览器扩展  <包目录>\extension\（manifest.json + background.js + content.js 三件）

标记约定：本包三份代码一致，条目不再区分实例；凡「实测」字样都是 2026-10-30 在 3080 上跑出来的。

【2. 跑的顺序】

先跑 S0 自检，再按 UB-A → UB-G 走。

  S0 自检（必须在实例插件体目录跑，不要在归档目录跑，理由见 UB-F-01）

      cd "<实例>\profiles\web\.dsh-launcher-plugin-bodies\dsh-ui-block"
      node self-check.mjs                     期望末行 self-check: 26 checks OK
      node self-check-uiblock-directive.mjs   期望末行 self-check-uiblock-directive: 46 assertions passed
      node self-check-element-chip.mjs        期望末行 dsh-ui-block element-chip self-check: all assertions passed
      node self-check.mjs --shot              需 4000 在跑；不在跑会打印 SKIPPED，不算通过

  然后 UB-A（指令与渲染）→ UB-B（元素 chip）→ UB-C（扩展卡片）→ UB-D（浏览器扩展）
      → UB-E（宿主路由）→ UB-F（自检与探针）→ UB-G（边界）。

  顺序上的三条硬约束：
    · B-12（画布内选区）依赖 UB-A 的块已经渲染出来，不能先跑。
    · UB-D 要真实浏览器装好扩展，与 DSH 实例无关，可以并行准备。
    · E-06（POST /reveal）会真的弹出资源管理器并选中目录，放到最后一条做。

  每条之间新开一条消息，或至少刷新页面：同一个页面上残留的块会污染 stats.blocks 与 live 数组的下标。

【3. 怎么触发（四种通道，条目里会指名用哪一种）】

  UI 通道     消息里的 ::dsh-ui 行、块横栏按钮、插件详情页的扩展卡片、composer、画布内选区图标。
  消息通道    发一条消息，正文里放独立一行的引用；res= 写在名字后面。
  文件通道    直接读写 <DSH_HOME>\ui-blocks\*.uiblock（改完 1.5 秒内画布应自己重绘）。
  接口通道    loopback HTTP，例如：
                Invoke-RestMethod http://127.0.0.1:3080/ui-block-extension
              3080 上这四条只读 GET 实测不需要 token；若某实例回 401，从 launcher.out.log 的
              dsh web: 行取 token 再带 ?token=。
  扩展通道    点浏览器工具栏图标 → 选元素 → 确定 → 粘进 composer。

【4. 判定标准】

  PASS     操作能重复做到；「期望」里列的每一项都观察到了（DOM 属性、精确文案、HTTP 状态码与
           JSON 字段、日志整行、文件内容与文件名、进程内计数），而不是「界面看起来正常」。
  PARTIAL  只对上一部分，必须写明哪一项没对上。
  FAIL     稳定复现的对不上。
  BLOCKED  跑不动（实例没起、机器没装 Edge、浏览器没装扩展、拿不到 token），不算失败。

  精确字符串逐字比对（例如「未声明，使用默认」「画布分辨率 820×510」「已打开：」「宽高要填正整数」），
  文案是模型与用户的输入，改一个字就是行为变更。
  数值型期望给容差：时间 ±0.5 秒；尺寸按整数像素；zoom 按 0.001 比较。

【5. 失败怎么记】

  每条失败照下面的模板记一行，写在单独的记录文件里，不要改本文件：

    [编号] FAIL | 实例 3080 或 4000 | 包版本 0.2.2 | 时间 | 会话 id
      现象：看到了什么（原文 / DOM 片段 / JSON / 截图路径）
      对照：源码 file:line 说的应该是什么
      复现：N/N 次

  硬规矩：本清单只做记录。发现缺陷不改代码、不改配置、不重启实例；
  任何修复都走「4000 改 → 4000 重启验证 → 才允许同步 3080 与归档」的顺序。

【本机限制】剪贴板不可观测
  实测：Set-Clipboard 'hello123' 后 Get-Clipboard -Raw 长度仍为 0；
        页面内 navigator.clipboard.readText() 返回 ""（writeText 不抛、hasFocus() 为 true）。
  受影响条目：A-13 / B-02 / B-08 / C-05 / D-10 / D-11 / D-14。
  这些条目的「剪贴板里是什么」在本机只能判 PARTIAL 或 BLOCKED，不是插件失败。
  换一台剪贴板正常的机器可以补测。

  说明（2026-10-30 实测修订，先读这一段）：指令只能出现在助手的 markdown 回复里 —— 那里才有 <p>。
  这是设计行为，不是缺陷，也不是待修项。

    桌面端的用户气泡由本插件自己的 conversation.chat.node（key=user、priority=-1）重绘成
      div.Sixlwa_userRow[data-element-chip-bubble=history] > div.Sixlwa_userStack > div.Sixlwa_bubble > span
    （white-space: normal，没有 <p> 元素）；而 sweep() 只扫 document.querySelectorAll('p, li')（client.js:1969-1991）。
    所以「用户发一条消息，正文里单独一行写 ::dsh-ui <name>::」这条路在桌面端永远不触发：那行只会原样
    显示成文字，不建画布，也不报错。引用由助手发出，用户气泡只负责显示与 chip 化（见 UB-B-05）。

    本分类所有条目按下面两句话读：
      · 「操作」里的发消息一律指「让助手在回复里输出以下 markdown」，由助手发出，不是用户发出；
      · 需要「画布已渲染」作前置的条目（A-09、A-12～A-16），先用一条助手回复把块引用出来，再动手。

九、已知问题 / 待观察
======================================================================

这一节只记录，不修。每条写「现在是什么样」和「看哪里」，供下次动手时定位。

K1. package.json 三份不一致（行为等价，发布前要统一）
   归档是 51 行：有 exports 段、没有 private；3080 与 4000 的插件体是 31 行：有 private:true、没有 exports。
   其余文件三份哈希完全相同，所以运行行为一致；但下次发布（npm pack / 打包归档）会以归档那份为准，
   实例体缺 exports 意味着按包名解析子路径（dsh-ui-block/client）在实例里不可用。
   相关条目：UB-G-08。

K2. 版本号三处不同步
   package.json 是 0.2.2、extension/manifest.json 是 0.2.2，但 client.js 暴露的 window.__dshPageBlock.version
   写的是 0.6.0（client.js:2116），README 里又出现 v0.4.0、0.2.3、0.2.0-rc.2 等字样。
   卡片文案「与插件 package.json 同版」并不做校验，它读的其实是 manifest；当前两者恰好相同，
   只改一处就会让这句文案变成假话。
   相关条目：UB-C-03、UB-F-09。

K3. README 说 node_modules 里是 junction，实测不是
   README:44 写「3080 的 profiles\web\node_modules\dsh-ui-block junction 指向 D:\dsh-plugins\dsh-ui-block」。
   2026-10-30 实测：该目录是普通目录（fsutil reparsepoint query 报 4390「不是重解析点」），
   且内容与归档哈希一致。也就是说现在有三份实体副本（归档、3080、4000），改代码必须三处同步，
   而 index.js:63-67 的注释仍按「junction 会被 realpathSync 折回包体」来论证路由安全。
   路由安全结论仍成立（extensionDir 只由模块自身位置推导，不接受请求值），但注释的前提已经变了。
   相关条目：UB-C-04、UB-E-01、UB-G-08。

K4. 归档目录跑不了 self-check
   归档没有实例的 node_modules 解析链，node self-check.mjs 直接 ERR_MODULE_NOT_FOUND（@deepseek-ai/dsh-tools）。
   必须在实例插件体目录跑；README 的「安装到 4000」一节没有写这一点。
   相关条目：UB-F-01。

K5. README 有大段已退役实现的记录，容易照着旧文档测
   「触发与元信息（v0.3.0）」「围栏块 / 横栏钩子」「scripts/check-meta.mjs」等段落描述的是旧围栏方案；
   现码只有 ::dsh-ui 行触发，scripts/ 目录已不存在。测试以本清单与源码为准，README 只当历史读。
   相关条目：UB-A-04、UB-A-05、UB-A-06。

K6. 工具描述里「用 write 创建的文件找不到」与实现不符
   create_ui_block 的说明写「a block that was not created through this tool has no registered metadata,
   so read_ui_block and the reference line cannot find it」，但代码里没有任何元数据登记表：
   读路由只查文件是否存在（index.js:496-503、722-724），客户端只按路径取（client.js:2054-2075）。
   直接 write 出来的 .uiblock 能正常渲染、也能被 read_ui_block 截图，只是历史基线在首次读取时才建。
   风险：模型被这段描述约束，用户手工放进去的块会被误认为「不生效」。
   相关条目：UB-A-18。

K7. 截图工具硬依赖 Windows 上的 Edge
   screenshotBlock 只认两条固定路径（Program Files 与 Program Files (x86) 下的 msedge.exe），找不到就抛
   no Microsoft Edge found at …；另外还要求 profile 里同时有 webServer、connection、attachments 三个服务，
   缺一个就直接报错并且明确要求不要重试（index.js:662-670）。UI 渲染不受影响，只有 read_ui_block 受影响。
   相关条目：UB-F-03。

K8. 历史补丁链超过 4MB 会被截断，?at= 可能给出错版
   readHistory 对超过 LOG_MAX_BYTES（4MB）的 log 只读前 4MB（index.js:259-263），被切掉的补丁不再回放；
   对截断点之后的 ?at= 请求会安静地返回较旧的版本，不报错也不打日志。
   代码自己标了 ponytail，升级路径是定期 checkpoint 新基线，但计划里被推迟了。
   相关条目：UB-E-10、UB-E-12。

K9. ?pin= 写 pins 失败时仍回 live，客户端无从察觉
   pinMoment 抛错时被 catch 住，moment 保持 null（index.js:745-750），于是返回最新内容并把
   x-uiblock-at 写成 live；客户端只按 200 处理，会以为拿到的是冻结版本。
   .pins.json 也只增不减：删掉块之后对应的键仍在，任意 nodeKey 都能让它长一条。
   相关条目：UB-A-10、UB-E-11。

K10. 跨 frame 选区只支持同源、一层嵌套
    content.js:61-75 的 ponytail 注释写明：跨源或更深嵌套的 iframe 上报的坐标是 (0,0)，
    高亮框会画错位置（选中本身仍可能成功）。这是已声明的上限，不是新缺陷。
    相关条目：UB-D-03。

K11. 扩展 manifest 的 default_title 是英文，卡片文案是中文
    manifest 里是 Pick an element → clipboard，卡片标题是「浏览器扩展 dsh-element-picker」。
    不影响功能，只是同一个东西两个名字，用户按中文名去工具栏找会找不到。
    相关条目：UB-C-07、UB-D-01。

K12. 备份文件只增不减
    create_ui_block 每次覆盖同名块都会留一份 <name>.uiblock.bak-<ISO 时间>（index.js:105-108），
    3080 的 ui-blocks 里已经有 50KB 级的备份；没有任何清理或上限。
    这些文件不会被当成块（UB-G-09），但会一直占盘。
    相关条目：UB-G-09。
